# Musterstadt Bürgerportal — Implementation Plan

## Overview

Build a realistic, deliberately legacy German municipal citizen portal as a **"before" demo asset** for Java modernisation workshops. The app must look and feel like it evolved organically over 15+ years — functional but visibly outdated — so that the modernisation story lands clearly.

**Runtime:** Open Liberty (Jakarta EE 8 / Java EE 8 compatibility profile)
**Java:** 8
**Build:** Maven 3.x
**Persistence:** JPA/Hibernate + H2 in-memory (clean state per restart)
**UI:** JSF 2.2 + PrimeFaces 6.x
**Structure:** Single Maven WAR project
**Package root:** `com.musterstadt`
**Locale:** German (`de_DE`) — dates as `dd.MM.yyyy`, decimal comma, currency `€`
**Login:** Single hardcoded credential — `buerger` / `Musterstadt2024`

**Non-goals:**
- No front/back split at this stage
- No security hardening
- No production deployment concerns
- No real file upload storage (path stored as string only)
- No i18n framework — German strings hardcoded directly in XHTML (authentically lazy legacy)

### Sub-Task 1 — Maven Project Scaffold + Open Liberty Config

**Status:** `[ ] pending`

**Expected Outcomes**

**Todo List**

   - `liberty-maven-plugin` for `mvn liberty:run`
2. Create `src/main/liberty/config/server.xml` with:
   - `webProfile-8.0` feature (covers JSF 2.2, JPA 2.2, CDI 2.0, Servlet 4.0)
   - `jndi-1.0` feature
   - In-memory H2 JDBC datasource config bound to `jdbc/buergerportal`

4. Create `src/main/webapp/WEB-INF/faces-config.xml` (empty skeleton with navigation rules placeholder)

**Relevant Context**

- PrimeFaces 6.2 JAR must be bundled (not provided by Liberty)
- H2 driver JAR must be available to Liberty's classloader — add as shared library in `server.xml` or drop into the WAR's `WEB-INF/lib`

### Sub-Task 2 — Data Model + JPA Entities + Seed Data

**Status:** `[ ] pending`

**Intent**  
Define the four JPA entities from the spec and seed realistic German test data on startup. Realistic data makes the demo credible.

**Expected Outcomes**
- `Citizen`, `Application`, `ParkingPermit`, `DogRegistration` entities created and mapped
- Schema auto-generated by Hibernate on boot
- At least 10 seeded citizens and a spread of registrations across all services

**Todo List**
1. Create entity classes in `src/main/java/com/musterstadt/model/`:
   - `Citizen` — id, firstName, lastName, street, houseNumber, postcode, city, email, phone
   - `Application` — id, citizen (ManyToOne), type (enum: PARKING, ADDRESS, DOG), status (enum: PENDING, APPROVED, REJECTED), createdDate, lastUpdated
   - `ParkingPermit` — id, application (OneToOne), vehicleRegistration, zone, proofDocumentPath
   - `DogRegistration` — id, citizen (ManyToOne), dogName, breed, registrationDate
2. Create `DataInitializer` — a `@Singleton` EJB with `@Startup` that uses the `CitizenDao` / `EntityManager` to insert seed data if the table is empty
3. Seed data: 10–15 citizens with authentic German names/addresses (e.g. Müller, Schmidt, Schneider; streets like Hauptstraße, Bahnhofstraße; postcodes 80xxx München range), 5+ parking applications (mixed statuses), 8+ dog registrations (mixed breeds including Schäferhund, Labrador, Dackel), 3+ address applications
4. All dates stored as `java.util.Date`; displayed in views as `dd.MM.yyyy` using `<f:convertDateTime pattern="dd.MM.yyyy" timeZone="Europe/Berlin" />`

**Relevant Context**
- Use `@GeneratedValue(strategy = GenerationType.IDENTITY)` for H2 compatibility
- `@Startup @Singleton` EJB fires after persistence unit is ready — safe for seeding

### Sub-Task 5 — Managed Beans (JSF Backing Beans)

**Status:** `[ ] pending`

**Intent**  
Create JSF managed beans using the legacy `@ManagedBean` annotation (not CDI `@Named`) with deliberately wide scopes. Business logic leaks into beans to demonstrate the anti-pattern.

**Expected Outcomes**
- All four service workflows have a backing bean
- Beans use `@SessionScoped` where it creates obvious problems
- Submit methods contain inline validation (length checks etc.) before delegating to service

**Todo List**
1. Create `src/main/java/com/musterstadt/bean/`:
   - `ParkingPermitBean` — `@ManagedBean @SessionScoped` — fields: vehicleRegistration, zone, proofDocumentPath, currentApplication; methods: submitApplication (inline `if(vehicleRegistration.length() < 5)`), loadApplication, clearForm
   - `AddressChangeBean` — `@ManagedBean @RequestScoped` — fields: street, houseNumber, postcode, city; methods: submitChange, validateAndSubmit (does both validation and save)
   - `DogRegistrationBean` — `@ManagedBean @ViewScoped` — fields: dogName, breed, searchQuery, results (List); methods: registerDog, search, clearSearch
   - `DashboardBean` — `@ManagedBean @RequestScoped` — loads counts for dashboard stats
   - `LoginBean` — `@ManagedBean @SessionScoped` — single hardcoded credential (`buerger` / `Musterstadt2024`), sets session attribute `loggedIn=true`; any other input shows `"Anmeldung fehlgeschlagen. Bitte versuchen Sie es erneut."`
2. Add TODOs in ParkingPermitBean:
   - `// TODO: Support mobile users`
   - `// TODO: Replace JSF wizard with modern flow`
3. Navigation: use `faces-config.xml` `<navigation-rule>` entries (string outcome returns) rather than implicit navigation

**Relevant Context**
- `@ManagedBean` is from `javax.faces.bean` — deliberately avoiding CDI `@Named` to look legacy
- `@SessionScoped` on ParkingPermitBean means if you open two tabs, state bleeds — intentional demo problem
- All user-facing strings in XHTML in German; field labels, button text, error messages all hardcoded in German

### Sub-Task 7 — CSS + Legacy Styling

**Status:** `[ ] pending`

**Intent**  
Write a single CSS file that makes the portal look unmistakably early-2000s government: blue gradients, grey backgrounds, Arial 12px, table borders, no flexbox or grid.

**Expected Outcomes**
- Visual immediately reads as "legacy desktop portal"
- No media queries
- Blue gradient header, grey sidebar, white content area
- Poor colour contrast (light grey text on white background in places)

**Todo List**
1. Create `src/main/webapp/resources/css/portal.css`:
   - Body: `font-family: Arial, Tahoma, sans-serif; font-size: 12px; background: #e8e8e8;` — no `lang` attribute in CSS, but `<html lang="de">` in layout template
   - `#wrapper`: `width: 960px; margin: 0 auto;`
   - `#header`: blue gradient (`background: linear-gradient(#003399, #0055cc)`), white text, fixed height
   - `#nav`: grey background (`#cccccc`), border, `width: 200px`, small font
   - `#content`: white background, padding, no max-width constraint
   - Table styles: `border: 1px solid #999`, `cellspacing`-era look
   - Form labels: no padding, tight spacing
   - Error messages: `color: red; font-size: 11px` (contrast fail)
   - Link colour: `#000080` (navy, low contrast on grey)
2. Create `src/main/webapp/resources/js/portal.js` — empty file with a single comment: `// Legacy portal JS - do not modify`
3. Ensure no CSS resets or normalisation — raw browser defaults show through
